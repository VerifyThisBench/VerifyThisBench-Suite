METHODOLOGY - Specification Evaluation:
Your goal is to extract the current specifications (preconditions and postconditions) from the implementation and evaluate them against the test case values to determine if the specs are correctly defined.

For each test case:
1. **Extract the relevant specification** (precondition or postcondition) from the original implementation
2. **Substitute the test case values** into the specification
3. **Evaluate if the result matches the expected outcome**:
   - If test case has "expected": true, the specification should evaluate to true with the given values
   - If test case has "expected": false, the specification should evaluate to false with the given values
4. **Use assert to validate** that the specification behaves as expected

EXAMPLES of Specification Evaluation:
- If generated postcondition is `result >= 10` but test case has output = 9 and expected = true, then the spec is wrong (9 >= 10 is false, but we expect true)
- If precondition is `a != 0` and test case has array = null with expected = false, then we verify the spec correctly rejects null arrays
- If postcondition is `0 <= result && result < n` and test case has result = 5, n = 6, expected = true, then we verify 0 <= 5 < 6 evaluates to true

The test functions should plug in the test case values and verify that the specification evaluates to the expected boolean result.

VeriFast-specific guidelines:
- Create individual test functions for each test case: `void test_t001()` where t001 is the test ID from the JSON
- Call all test functions from a main() function
- Add contracts to test functions: `//@ requires true; //@ ensures true;`
- Use `//@ assert(spec_condition);` for positive tests (expected: true)

- Handle memory predicates and separation logic properly

- Use `malloc` and `free` with proper annotations for dynamic allocation

QUANTIFIER NEGATION RULE:
When testing that a universal condition should be false (expected: false), instead of asserting the negation of the entire condition, find a specific counterexample and assert that the condition fails at that point. This is more readable and logically clearer in VeriFast.

Transformation approach:
- Original postcondition checks: for all i in [0, n): a[result] >= a[i]
- When it should be false, find specific index i where a[result] < a[i]
- Assert the counterexample: `//@ assert(a_values[result_index] < a_values[counter_index]);`

Example:
- Original: for all i in [0, n): a[result] >= a[i]
- When false with result_index=0 and array [5,2,8,1,9,3]:
  Counterexample at index 4: a[0]=5 < a[4]=9
  `//@ assert(nth(0, values) < nth(4, values));`

SPECIAL NULL HANDLING INSTRUCTIONS:
When testing for null values in PRECONDITIONS only:
- Declare nullable pointers: `int *test_array = 0;`
- For non-null precondition tests, allocate and initialize: `int *test_array = malloc(6 * sizeof(int)); if(test_array == 0) abort(); ...`
- Compare using `!= 0` or `== 0` (VeriFast uses 0 instead of NULL)
- Remember proper memory cleanup with `free()` and separation logic annotations

For POSTCONDITION testing, use regular non-null arrays since postconditions assume preconditions have already been satisfied.
