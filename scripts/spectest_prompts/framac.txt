4. Test both positive (should pass) and negative (should fail) scenarios

METHODOLOGY - Specification Evaluation:
Your goal is to extract the current specifications (preconditions and postconditions) from the implementation and evaluate them against the test case values to determine if the specs are correctly defined.

For each test case:
1. **Extract the relevant specification** (precondition or postcondition) from the original implementation
2. **Substitute the test case values** into the specification
3. **Evaluate if the result matches the expected outcome**:
   - If test case has "expected": true, the specification should evaluate to true with the given values
   - If test case has "expected": false, the specification should evaluate to false with the given values
4. **Use assert to validate** that the specification behaves as expected

EXAMPLES of Specification Evaluation:
- If generated postcondition is `\result >= 10` but test case has output = 9 and expected = true, then the spec is wrong (9 >= 10 is false, but we expect true)
- If precondition is `a != \null` and test case has array = null with expected = false, then we verify the spec correctly rejects null arrays
- If postcondition is `0 <= \result < n` and test case has result = 5, n = 6, expected = true, then we verify 0 <= 5 < 6 evaluates to true

The test functions should plug in the test case values and verify that the specification evaluates to the expected boolean result.

Frama-C/ACSL-specific guidelines:
- Create individual test functions for each test case: `void test_t001() { ... }` where t001 is the test ID from the JSON
- Call all test functions from a main() function
- Use `/*@ assert spec_condition; */` for positive tests (expected: true)
- Use `/*@ assert !spec_condition; */` for negative tests (expected: false)
- Handle arrays and pointers appropriately
- Use `\forall` and `\exists` quantifiers as needed
- Handle pointer validity with `\valid()` predicates
- Include proper memory safety checks
- Add ghost variables if needed: `/*@ ghost type var = value; */`
- Ensure proper memory allocation and deallocation

QUANTIFIER NEGATION RULE:
When testing that a `\forall` condition should be false (expected: false), instead of using `/*@ assert !(\forall ...) */`, 
use `/*@ assert \exists */` to find a counterexample. This is more readable and logically clearer.

Transformation rule:
- Original: `\forall integer i; P(i) ==> Q(i)`
- When it should be false, instead of: `/*@ assert !(\forall integer i; P(i) ==> Q(i)); */`
- Use: `/*@ assert \exists integer i; P(i) && !Q(i); */`

Example:
- Original: `\forall integer i; 0 <= i < n ==> a[max] >= a[i]`
- When false, instead of: `/*@ assert !(\forall integer i; 0 <= i < n ==> a[max] >= a[i]); */`
- Use: `/*@ assert \exists integer i; 0 <= i < n && a[max] < a[i]; */`

SPECIAL NULL HANDLING INSTRUCTIONS:
When testing for null values in PRECONDITIONS only:
- Declare nullable pointers: `int *test_array = NULL;`
- For non-null precondition tests, allocate the actual array: `int *test_array = malloc(6 * sizeof(int)); test_array[0] = 5; ...`
- Compare using `!= \null` or `== \null` as appropriate
- Use `\valid()` predicates for validity checks
- Remember to free allocated memory

For POSTCONDITION testing, use regular non-null arrays since postconditions assume preconditions have already been satisfied.

For each test function, add a comment at the beginning that clearly describes what is being tested. Do not use printf statements. Use this format:

- For postcondition tests: `// TestT001: Testing postcondition: [condition description] with input [input values] and result [result value] - expected: [true/false]`
