METHODOLOGY - Specification Evaluation:
Your goal is to extract the current specifications (preconditions and postconditions) from the implementation and evaluate them against the test case values to determine if the specs are correctly defined.

For each test case:
1. **Extract the relevant specification** (precondition or postcondition) from the original implementation
2. **Substitute the test case values** into the specification
3. **Evaluate if the result matches the expected outcome**:
   - If test case has "expected": true, the specification should evaluate to true with the given values
   - If test case has "expected": false, the specification should evaluate to false with the given values
4. **Use assert to validate** that the specification behaves as expected

EXAMPLES of Specification Evaluation:
- If generated postcondition is `result >= 10` but test case has output = 9 and expected = true, then the spec is wrong (9 >= 10 is false, but we expect true)
- If precondition is `length a > 0` and test case has array = [] with expected = false, then we verify the spec correctly rejects empty arrays
- If postcondition is `0 <= result < length a` and test case has result = 5, length a = 6, expected = true, then we verify 0 <= 5 < 6 evaluates to true

The test functions should plug in the test case values and verify that the specification evaluates to the expected boolean result.

Why3-specific guidelines:
- Create individual test functions for each test case: `let test_t001 () = ...` where t001 is the test ID from the JSON
- Call all test functions from a main function: `let main () = ...`
- Use `assert { spec_condition }` for positive tests (expected: true)
- Use `assert { not (spec_condition) }` for negative tests (expected: false)
- Import necessary modules (int.Int, array.Array, array.ArrayMake, etc.)
- Handle array bounds and length checks properly
- Use proper typing for integers and arrays
- Create arrays using `Array.make n default_value` and set elements individually
- Use `forall` and `exists` quantifiers as needed
- Add ghost variables if needed for intermediate assertions
- Ensure all test functions have proper requires/ensures if needed

QUANTIFIER NEGATION RULE:
When testing that a `forall` condition should be false (expected: false), instead of using `assert { not (forall ...) }`,
use `assert { exists }` to find a counterexample. This is more readable and logically clearer.

Transformation rule:
- Original: `forall i. P(i) -> Q(i)`
- When it should be false, instead of: `assert { not (forall i. P(i) -> Q(i)) }`
- Use: `assert { exists i. P(i) /\ not Q(i) }`

Example:
- Original: `forall i. 0 <= i < length a -> a[max] >= a[i]`
- When false, instead of: `assert { not (forall i. 0 <= i < length a -> a[max] >= a[i]) }`
- Use: `assert { exists i. 0 <= i < length a /\ a[max] < a[i] }`

SPECIAL NULL HANDLING INSTRUCTIONS:
Why3 uses algebraic data types rather than null pointers. When testing for absent/invalid values in PRECONDITIONS only:
- Use `option` type for nullable values: `let test_array : option (array int) = None`
- For non-null precondition tests, use `Some`: `let test_array = Some (make 6 0)` then set elements
- Compare using pattern matching or `is_some` / `is_none` predicates
- The option type allows you to represent and test absence properly

For POSTCONDITION testing, use regular non-optional arrays since postconditions assume preconditions have already been satisfied.
